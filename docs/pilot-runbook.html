The weekly one-liner

All pilot_* reports, squad_duplicate_candidates and stale_pending_consent require the reviewed project's authorized operator SQL editor or a separate trusted server-side service_role connection. A club account uses authenticated, not service_role; denial with app credentials is expected. Never put service credentials in browser VITE_* configuration or the legacy seed/check clients.

BEGIN READ ONLY;
SET LOCAL ROLE service_role;
SELECT current_user;
SELECT * FROM public.pilot_scorecard;
ROLLBACK;

One row per pilot week, every metric above. This is the "answer it in under a minute" test from the scope.

Use this same authorized workflow for drill-downs, H4 bias checks and duplicate-roster reports. For S3, record the target project, deployed migration, querying role, configured academy/window and observed values. Permission alone does not establish correct numbers. The legacy checker skips restricted reports and cannot verify their contents or migration state.

What invalidates each number

Metric 2 returns no rows if the coach never enters fixtures. That is not a zero, it is an unmeasurable. Chase the fixture list in week 0, not week 4.

Metric 3 joins assessments to matches by player within 48 hours, because coach_assessments carries no match_id. A coach who assesses twice in one window has the first counted. Fine at pilot scale, not beyond it.

Metric 4 divides a quick-assess run across the squad. A coach who starts a run, puts the phone down and finishes an hour later poisons the median — check the week's outliers before reporting.

Metric 5 is derived, not blind: the coach may have seen the player's band before assessing. Capture a genuinely blind sample in the weekly call and compare against pilot_rating_agreement. If the two disagree sharply, the blind number is the truth.

Metrics 6 & 7 count any app open, and WhatsApp nudges inflate them — which is exactly why weeks 5–7 run unprompted. Report weeks 5–7 separately from 1–4 or the number means nothing.

Metric 8 must return zero rows. A row is not automatically a breach — a parent legitimately linked to two children in the academy trips the first check — but every row is explained in writing before the pilot continues.

The H4 bias check — run weekly from week 1

The scope predicts the engine under-rates goalkeepers and defenders. Run this whatever the headline says, so there is a dataset to recalibrate against.

SELECT position,
       count(*)                   AS n,
       round(avg(engine_bias), 2) AS avg_bias,
       round(100.0 * count(*) FILTER (WHERE agrees) / count(*), 1) AS agreement_pct
FROM pilot_rating_agreement_derived
GROUP BY position
ORDER BY avg_bias;

Negative avg_bias means the engine bands lower than the coach. A consistent negative for gk/def alongside a positive for att is the systematic bias the scope predicts — and it triggers Iterate, not Stop.

Part 6  Standing risks

Live throughout the pilot

Blocker

No notification layer

Nothing tells a coach a match needs assessing. WhatsApp nudges weeks 1–4, logged every time. Weeks 5–7 measure life without them.

Closed

Pitch-side connectivity

There is still no offline capture, so submitting needs a live connection — but the signal at the academy's ground is known to be good, from direct knowledge of the venue. No test needed. Revisit only if a coach reports a failed submission, since losing fifteen minutes of input is the fastest way to lose a coach.

Closed

The repo could not rebuild the database

user_role included 'club' in production but no migration added it, so applying this folder to an empty database produced a schema the app could not run on. 20260423999999_user_role_club_value.sql closes it, dated to sort immediately before the first migration that references the value. Still outstanding: backups have never been restore-tested — take a verified dump before week 0.

Closed

Stale generated types

38 type errors, now 0. The generated types were missing organizations, admin_notes, staff_compliance, two RPCs and eight columns added by later migrations, so the club and parent surfaces had no type safety at all. Fixing them also surfaced a real bug: navigator.share is non-optional in TypeScript's DOM lib but genuinely absent on desktop, so the parent-invite fallback was never type-checked.

Watch

Thin automated coverage

8 test files against 163 source files. Live data will find paths they do not. Keep a same-week fix loop in weeks 1–2 and expect to spend time there.

Closed

The scorecard counted the whole database

Caught by running the views against real data. Activation read 3.2% for a squad that was 54% claimed, because the cohort views counted every squad_players row and every parent invite in the database — demo academies, dev accounts, months of old seed data. Production will still hold all of it in September, so the real pilot's activation number would have been equally meaningless. All four cohort views now scope through pilot_config.org_id; the same data then read 60%.

Closed

Roster building — the UC-02 number

Add-player saved one player then navigated back to the squad list, so a fifteen-player roster cost fifteen round trips and asked fifteen times for an age group that is, by definition, one value for the whole squad. It now saves and stays: Save & add another clears the name, position and shirt, keeps the age group, and returns focus to the name field, with Enter as a shortcut. A roster_built event records players and elapsed time, so UC-02's stopwatch number lands in telemetry rather than on a notepad.

Match logging was audited too and is not the problem — both flows already default sensibly and offer select-all. The one real find there is below.

Closed

Quick match log flattened the squad

It wrote identical inputs for every attending player — 90 minutes, no goals, no assists, "Average" everything — so computed ratings varied only by position and an eighteen-player squad got about four distinct bands, the same ones every week. That hit H2 (a band that is not about you is not readable) and H4 (agreement with a per-player judgement approaches chance). Comparing the two flows settled it: CoachAddSession requires the same fields and defaults every player the same way, so the quick log saved exactly one tap. /coach/sessions/quick now resolves to the full session screen preset to Match — same effort, real per-player detail where it matters.

Closed

Player signup duplicated the roster

link_player_to_coach only looked for a row already linked to that player, so UC-02 (coach types the roster) followed by UC-03 (player signs up with the code) left two rows per player — one unclaimed ghost, one linked. It over-counted the club dashboard and halved activation, since pilot_activation treats every roster row as an invitation. Signup now adopts the coach's own entry when exactly one unclaimed row matches the name; two players sharing a name still fall back to inserting, because a wrong merge would hand one child another's history. Existing duplicates are surfaced by squad_duplicate_candidates rather than merged automatically.

Closed

Coach feedback was unreachable without a note

The feedback card on the player's home screen rendered only when an assessment carried a written note — and notes are optional for the coach. Worse, the edge function returned 404 No coaching note found, so the screen only appeared to work in development. A coach who assessed without typing anything left the player with band bars and no way in, which made UC-08 undemoable and left H2 — does written coach feedback land? — with no surface to be tested on. The card now shows for any assessment and the feedback works from the six category scores when there is no note.

Watch

Uncalibrated rating engine

Position modifiers were set by judgement, not fitted to data. Run the bias query weekly from week 1 so there is something to recalibrate against at week 8.
