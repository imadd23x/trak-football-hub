# Auth network recovery: scope and acceptance

Base: fork #8 `84ea139`. A separate built-app probe on that commit held the SDK refresh of an expired synthetic remembered session for 21 seconds. The page still showed “Checking your account…” with zero buttons and zero profile reads; releasing the token response immediately restored account choice. All backend traffic was intercepted. This failure precedes the profile-operation deadline.

The installed Auth SDK refreshes during initialization and may retry refresh requests with exponential backoff for a 30-second envelope. It also reads a session when emitting INITIAL_SESSION. A UI-only Promise.race does not cancel these requests and could permit a late response to replace another account. Do not alter SDK internals, fake an invalid-token HTTP response, clear a valid remembered account on a transient failure, or replace the admission architecture.

Implement an Auth-only fetch boundary on the existing persistent client: 20-second request/body deadline, propagated cancellation, response buffering before SDK consumption, and rejection of responses superseded by another stored account. A superseded refresh token must remain rejected through the SDK's retry envelope. Leave Data/Functions/Storage streaming unchanged. Keep HTTP status/error bodies for the SDK's normal classification. The initial-loading UI must offer a page retry after 20 seconds even while the SDK completes its retry cycle; a page retry restarts that lifecycle without deleting the remembered account. Explicitly test the underlying transport and late SDK storage effects, not just the button.

Acceptance and verification: reproduce baseline failures; real SDK tests for stalled headers/body, retry, sign-in and sign-out outcomes, preserved storage on temporary failure, stale cross-account responses and refresh retries; built-app expired-session recovery on phones with actual deadlines and page reload, no unexpected network request or browser exception. Preserve email confirmation, password recovery, staff activation and all-role journeys. Run focused/full source/harness/type/lint/build checks and fork CI. Existing database authorization, household interfaces and production settings are unchanged.

Rollout: a separate fork PR on fork #8, exact-head peer review, dependency composition and explicit production authorization. Before release this additive source change can be reverted; after release diagnose and forward-repair rather than restoring an indefinite wait or permitting stale session mutation. Record SDK retry duration separately from the 20-second UI/transport deadline; do not claim all SDK work stops at that deadline.

## Traced failures and local evidence

The first real-SDK transport tests used a pass-through fetch (the preceding branch's behavior): six failed and two positive controls passed. Failures covered stalled headers/body, sign-out never settling, and late password/logout/refresh responses modifying a newer account. Additional failing tests exposed (1) an account change between SDK retry attempts, (2) a delayed background retry outliving an initially proposed expiry for its account guard, and (3) an old INITIAL_SESSION failure clearing a newer completed sign-in while the newer session remained in storage.

The final implementation keeps failed refresh attempts associated with their original local identity through backoff and browser suspension. Complete successful session responses release the entry; failed entries remain only in the page's memory, not in persistent storage or logs. Elapsed wall-clock time alone cannot prove an SDK retry is finished. This is a cancellation boundary, not an authorization source: server verification, profile access and database policies remain authoritative. The AuthProvider ignores INITIAL_SESSION after a newer live Auth event has already established the account.

Final source checks: 15 new focused SDK/provider cases pass; all 538 source tests across 45 files and 17 harness tests pass. Typecheck and production build pass. Lint: zero errors, 131 inherited warnings. The unchanged #37 production-bundle checker scans 95 files, 81 readable files and 77 named chunks without dev-only modules or burned credential values. The optional use-case runner still reports three obsolete UC-A02 failures, ten passing cases and 15 pending cases without tests; its success exit code is not proof those failed cases passed. Tarek retains the separately authorised coach-only retirement task.

Limits: the 20-second deadline covers each Auth HTTP request including its body, and the startup recovery control; it does not disable the SDK's internal retry/backoff or pretend all SDK work ends at 20 seconds. Page retry replaces that lifecycle without deleting the remembered account. A server-side sign-in, refresh or revocation may already have happened even when its response is lost. Browser storage values are used to cancel stale work, never to authorize academy or child access. This is not hosted Auth/email, production, pilot capacity or academy-departure verification.

All 44 registered browser journeys pass on the final production build. The six new journeys cover expired-session startup at `/` and `/settings`, real 20-second sign-in/sign-out failures with successful retries, and actual second-tab sign-in/sign-out transitions. They assert request abortion, preserved/current stored identity, usable navigation, and no unexpected requests or browser exceptions. Inspected 320px/390px startup recovery screenshots; controls remain visible without horizontal overflow.

Two browser test setup issues were corrected without weakening application assertions: initialization must not access localStorage in a new tab's opaque `about:blank` document, and the second-tab logout journey must explicitly allow the SDK's observed five-second lock recovery. Both tabs now initialize first; the subsequent sign-in control has a ten-second wait for that SDK step. The final full run passes. An ordinary account-choice/reload journey took 5.4 seconds in that run; a separately traced rerun took 472ms and contained no Auth lock/error console messages. This does not establish a latency budget or diagnose that slow sample; CAP-01 traces remain necessary.

Independent review and exact-head CI remain separate gates. No production merge, deployment, Auth configuration or real account was changed.
