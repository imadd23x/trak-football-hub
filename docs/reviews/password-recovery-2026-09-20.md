## Result and cause

The old route retried `getSession` once and could keep displaying verification indefinitely. It accepted a remembered account without identifying it, did not distinguish an error-bearing recovery URL from a usable link, and submitted through the mutable shared `updateUser` session. Thrown saves could leave the button disabled; the delayed success redirect could outlive the screen.

The replacement names the account verified by Auth, re-verifies its expected ID at submission and sends only `{ password }` using that same captured JWT. It cancels waiting work on account changes/navigation, prevents duplicate submits, bounds verification and saving to 20 seconds, and distinguishes an unknown save outcome from a rejected password. The shared accessible password control and existing validation are reused. A valid remembered session can still change its own password; requiring a particular recovery event would incorrectly reject legitimate authenticated changes and events received before the lazy route mounts. See [Supabase password updates](https://supabase.com/docs/reference/javascript/auth-updateuser) and [password recovery](https://supabase.com/docs/guides/auth/passwords).

A further built-app regression traced a provider bug: after A→B on the reset route and a correctly B-bound password save, account choice still displayed A and requested A's parent links using B's JWT. Both pending-GET and pending-PUT cases failed. `AuthContext` had suppressed `SIGNED_IN` on reset. The narrow correction keeps normal session/profile hydration and cache invalidation on this route; a `PASSWORD_RECOVERY` event only redirects when not already there. Confirmation, staff activation and ordinary sign-in remain covered by the full browser set.
