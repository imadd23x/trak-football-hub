## Implementation and reproduced failures

The dependency merge is `f9f1d5d`: #48 `43db21e` composed cleanly onto fork #6 `5c4fb07`. The 53 existing Settings/Auth regression checks and typecheck pass on that composition before new behavior was added. Existing Settings field isolation, account-bound writes and queued sign-out checks are preserved.

The new request helper uses a non-persistent, uniquely scoped SDK client with URL/session detection and automatic refresh disabled. It does not read or replace the shared browser session. Its 20-second deadline covers recipient verification, request and body parsing; an abortable wait also stops waiting for an SDK operation without an AbortSignal argument. Before any subsequent send, the operation checks cancellation again. Temporary SDK visibility listeners are removed after initialization.

Settings retains #48's operation guard, keyed form and `assertSettingsAccount` recheck. Only this reset action's identity lookup changes to fork #6's already-tested `checkPasswordAccount(signal)`: an additional regression proved that merely ending the UI wait left #48's underlying Auth GET running. The corrected test observes that GET abort and confirms a late response cannot send email. Other Settings operations keep their existing helper. Landing captures and validates the entered address, prevents concurrent sends, and clears/aborts pending feedback on input changes, sign-in and navigation. Replies appear inline with accessible status/error roles. No acknowledgement claims delivery; missing-account errors use the same acknowledgement, provider details are not exposed and uncertain outcomes advise checking the inbox before retrying.

References: [Supabase reset-password request](https://supabase.com/docs/reference/javascript/auth-resetpasswordforemail), [Auth rate limits](https://supabase.com/docs/guides/auth/rate-limits). No provider limits or retry duration are inferred from defaults or changed here; the UI handles HTTP 429 and never resends automatically.
